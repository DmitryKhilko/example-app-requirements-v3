# Памятка: Как писать Use Case без привязки к интерфейсу

## 1. Золотое правило «Чёрного ящика»

Use Case описывает **цель пользователя** и **диалог «Намерение — Реакция»**, но не то, как система устроена внутри или 
как выглядят её экраны. Если дизайнер перерисует кнопки или заменит веб-интерфейс на мобильное приложение, текст 
сценария должен остаться актуальным.

## 2. Словарь замен: Как уйти от UI

| ❌ Плохо (Привязка к UI и коду) | ✅ Хорошо (Намерение и бизнес-логика) |
| :--- | :--- |
| Нажимает кнопку «Сохранить» | Подтверждает сохранение данных |
| Вводит текст в поле «Поиск» | Задает критерии поиска |
| Включает чекбокс / тоггл «Архив» | Запрашивает отображение архивных записей |
| Выбирает из выпадающего списка | Указывает значение из доступного перечня |
| Переходит по ссылке / открывает вкладку | Запрашивает переход к разделу / карточке |
| Видит красную рамку и `MSG:err_01` | Система уведомляет об ошибке валидации |
| Отображаются первые 20 записей | Система предоставляет список с постраничной навигацией |

## 3. Пять правил написания шагов

1. **Правило пинг-понга:** Чередуйте шаги строго по схеме *«Актор делает → Система отвечает»*. Не склеивайте действие и 
реакцию в одно предложение.
2. **Никаких «магических чисел»:** Конкретные лимиты (20 строк, 255 символов, 5 минут) живут в спецификациях 
функциональностей (`F` или `SF`). В UC пишите общими словами (например, *«в пределах допустимого лимита»*).
3. **Абстрагируйтесь от способа ввода:** Неважно, ввел пользователь данные с клавиатуры, отсканировал штрихкод или 
выбрал мышкой. Пишите: *«Пользователь предоставляет данные»* или *«Пользователь указывает параметры»*.
4. **Не пишите про техническую «подкапотку»:** Фразы вроде *«запись в журнал аудита не производилась»* или 
*«отправляется GET-запрос»* — это нефункциональные требования или детали реализации, а не цель пользователя.
5. **Фокус на успешном пути:** Основной поток — это идеальный сценарий, когда всё прошло без ошибок. Любые отклонения, 
отмены и ошибки уносите в альтернативные потоки.

## 4. Эталонный шаблон Use Case

```markdown
### UC-[МОДУЛЬ]-[НОМЕР]. [Название: Глагол + Существительное]

**Описание:** Краткая бизнес-цель (зачем пользователь это делает и какой результат хочет получить).
**Актор:** Роль пользователя или внешняя система, инициирующая сценарий.
**Использует:** Ссылки на спецификации, где описаны детали полей, валидации и API.
**Предусловие:** Что должно быть истинным *до* начала сценария (например, наличие прав, существование записи).

**Основной поток:**
1. Актор запрашивает [действие / раздел].
2. Система предоставляет [данные / форму для заполнения].
3. Актор указывает [необходимые параметры / данные] и подтверждает действие.
4. Система проверяет корректность данных, сохраняет изменения и информирует актора об успехе.

**Альтернативные потоки:**
* **А1. [Название отклонения] (на шаге X):**
  1. Условие возникновения (например, *данные не прошли проверку*).
  2. Реакция системы (например, *система отклоняет операцию и информирует актора о причине*).
  3. Возврат в основной поток (например, *сценарий возвращается к шагу 3*) или завершение.

**Постусловие:** Изменение состояния данных в системе после успешного завершения основного потока (например, 
*в справочнике создана новая активная запись*).
```
