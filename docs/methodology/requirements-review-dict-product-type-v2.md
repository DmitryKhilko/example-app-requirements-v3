# Анализ качества требований: справочник видов изделий {#requirements-review-dict-product-type}

## Обзор {#overview}

Документ фиксирует результат проверки требований к справочнику видов изделий (`F-PT`) по десяти критериям качества
и предложения по выносу общих требований на уровень основной функциональности и на глобальный уровень.

- **Дата анализа**: 24.11.2026.
- **Версия требований**: репозиторий `example-app-requirements-v2`, ветка `main`, коммит `60b7f9c`.
- **Объём**: `index.md`, `uc.md`, `ui.md` и шесть детальных функциональностей (`SF-PT-LIST`, `SF-PT-READ`,
  `SF-PT-CREATE`, `SF-PT-UPDATE`, `SF-PT-ACTIVATION`, `SF-PT-DELETE`) — 46 пунктов требований, 157 сценариев приёмки
  (из них 10 ручных `@manual` и 24 нефункциональных `@NFR`), 36 допущений и вопросов.
- **Способ проверки**: чтение всех пунктов, автоматическая сверка ссылок, якорей, идентификаторов и `data-testid`,
  проверка JSON-эталонов по схемам, пересчёт ожиданий AC на тестовом наборе.

Итог: структура и трассировка внутри справочника в порядке — идентификаторы уникальны, битых ссылок нет, у каждого FR
есть AC, каждый `data-testid` из AC описан. Основные слабые места: связь с источником (справочник ссылался на чужую
бизнес-цель), 30 неподтверждённых допущений и дублирование одних и тех же правил в нескольких SF.

## Критерии {#criteria}

| Критерий | Что проверяется |
| :--- | :--- |
| Недвусмысленность | Формулировка допускает одно толкование для заказчика, аналитиков, разработчиков и тестировщиков |
| Проверяемость | Соответствие можно однозначно подтвердить тестом, осмотром, анализом или демонстрацией |
| Атомарность | Пункт описывает одно неделимое условие или действие |
| Непротиворечивость | Пункт не конфликтует с другими требованиями, бизнес-правилами и ограничениями |
| Выполнимость | Пункт осуществим в рамках сроков, бюджета и доступных технологий |
| Полнота | Есть всё для реализации и проверки, нет пропущенных условий и заглушек |
| Трассируемость | Видна связь с источником (бизнес-цель, сценарий) и с последующими артефактами |
| Модифицируемость | Пункт меняется с минимальными трудозатратами и без новых противоречий |
| Приоритетность и стабильность | Определены важность для бизнеса и вероятность изменения |
| Уникальность и актуальность | Есть собственный идентификатор, пункт отражает текущие потребности |

## Сводная оценка {#summary}

| Критерий | Оценка | Основные замечания |
| :--- | :--- | :--- |
| Недвусмысленность | Частично | Роли не определены; «ё» в поиске и сортировке; внутренние пробелы; «тип» и «группа» |
| Проверяемость | В основном да | Не задан тестовый стенд NFR; часовой пояс тестов; правило для будущих документов |
| Атомарность | Частично | Несколько FR объединяют разные правила |
| Непротиворечивость | Есть конфликты | Точность `updated_at`; расхождения с дизайн-системой; uc.md отстаёт от FR |
| Выполнимость | Да, с оговоркой | Проверка одновременного изменения не работала бы при прежнем формате дат |
| Полнота | Частично | 30 неподтверждённых допущений, 1 открытый вопрос; пустые `SF-G-TOAST` и файлы уровня F; аудит |
| Трассируемость | Внутри — да | Связь с источником нарушена: F-PT ссылался на BG-001 об обмене накладными |
| Модифицируемость | Слабо | Сущность, перечень типов, правила проверки и формат ошибок продублированы |
| Приоритетность и стабильность | Слабо | У всех SF приоритет `must`, стабильность не задана |
| Уникальность и актуальность | Да, с хвостами | ID уникальны; остались мусор и устаревшие пометки |

## Замечания по критериям {#findings}

### Недвусмысленность {#unambiguity}

1. Роли `ais`, `pgipn`, `sgipn`, `igipn`, `pko`, `psh` нигде не расшифрованы. Из-за этого неясен сценарий READ
   «пользователь без разрешённой роли»: если смотреть могут все роли, кто получает `403`?
2. «Без учёта регистра» и «по правилам русского алфавита» не уточняют, равны ли «е» и «ё» при поиске, проверке
   уникальности и сортировке, и как сортируются цифры и латиница.
3. Пробелы обрезаются только по краям: не определено, дубликаты ли «Кольца разные» и «Кольца  разные».
4. В интерфейсе и UC — «тип изделия», в сообщении API об ошибке `409` и в допущении о уникальности — «группа».
5. В глоссарии нет предметных терминов: вид изделия, тип изделия, натир, наложенный оттиск.

### Проверяемость {#verifiability}

1. Показатели времени (500 мс, 200 мс, 1 с) измеряются «на тестовом стенде», но стенд не описан; объём «10 000
   записей» не имеет источника.
2. AC экрана ожидают время в UTC+3 («18.11.2026 16:23:51»), что зависит от часового пояса браузера: часовой пояс
   тестового окружения нужно зафиксировать.
3. `FR-PT-ACTIVATION-001`: правило «недействующая запись не предлагается в новых документах» сейчас не проверить —
   документов, которые выбирают вид изделий, ещё нет.
4. «Текст `message` без технических подробностей» проверяется только осмотром; axe-core покрывает WCAG частично.
   Десять сценариев `@manual` нужно перенести в план ручного тестирования.

### Атомарность {#atomicity}

1. `FR-PT-LIST-002` объединяет поиск и четыре вида фильтров.
2. `FR-PT-LIST-005` описывает экран целиком: переход, заголовок, таблицу, пагинацию, шесть состояний, UX и 15
   сценариев.
3. `FR-PT-DELETE-001` объединяет определение «используется», неделимость, пропуск отсутствующих записей и аудит.

Стандарт допускает описывать экран одной SF внутри FR, но изменение одного правила меняет большой пункт и его AC.

### Непротиворечивость {#consistency}

1. **Точность `updated_at` (критично).** `DR-PT-UPDATE-001.H01` сравнивал `updated_at` с точностью до микросекунд, а
   эталоны API и тестовый набор передают время до секунды. При хранении микросекунд проверка одновременного
   изменения всегда отвечала бы `409`.
2. **Дизайн-система расходилась с требованиями**: значения по умолчанию в форме создания («0,5 и 0» против 1),
   размеры страницы (10, 25, 50 против 10, 25, 50, 100), конец периода фильтра (23:59:00 против 23:59:59),
   состояния таблицы помечены допущениями.
3. **uc.md отставал от FR**: `UC-PT-004.H01` оставался открытым, хотя `FR-PT-LIST-007.H03` его закрывает;
   `UC-PT-005.H01` фактически решён в `FR-PT-LIST-007`.
4. Описание F-PT называло справочник «перечнем ювелирных изделий», хотя в нём есть весовые изделия и часовые корпуса.

### Выполнимость {#feasibility}

Всё реализуемо. Оговорки: проверка одновременного изменения при прежнем формате дат (см. выше) и индексы,
рассчитанные на PostgreSQL с расширением `pg_trgm` — СУБД нужно подтвердить.

### Полнота {#completeness}

1. 30 допущений «требует подтверждения» и вопрос `UI-PT-001.Q01`; больше всего — по экрану списка (12) и удалению (5).
2. Аудит обещан в границах F-PT и в нескольких FR, но не описано, что пишется в журнал, сколько хранится и кто читает.
3. `SF-G-TOAST` пуст, хотя на него ссылаются тексты, время показа и `data-testid` уведомлений.
4. Файлы уровня F `dr.md` и `fr.md` пусты.
5. У создания нет показателя времени ответа; в DR нет верхнего предела оттисков; на диаграмме последовательности
   нет изменения записи.

### Трассируемость {#traceability}

1. F-PT ссылался на BG-001 «Электронный обмен накладными через EDI» — цель другого продукта; своей бизнес-цели и
   критериев успеха у справочника не было.
2. Внутри справочника цепочка F → UC → SF → DR, FR, AR → AC → JSON-эталоны полная.
3. Связи с задачами и кодом нет (`task_id`, `release_id` пустые) — для этапа «анализ» это допустимо.

### Модифицируемость {#modifiability}

1. Состав сущности описан в трёх DR детальных функциональностей.
2. Перечень трёх типов изделий повторён в двух DR, пяти JSON-схемах, `UI-PT-001` и `FR-PT-LIST-006`.
3. Эталоны ответов `401`, `403`, `500` одинаковы в пяти SF.
4. Общие правила лежат в одной SF: правила `data-testid` и тестовый набор — в `SF-PT-LIST`, поведение при `401` —
   допущение `FR-PT-LIST-005.H03`, на которое ссылаются другие SF.
5. Карточка `SF-PT-CREATE` устроена иначе, чем остальные: нет «Границ» и «Состава требований».

### Приоритетность и стабильность {#priority}

1. У всех шести SF приоритет `must`: нельзя понять, что можно отложить при поэтапной сдаче.
2. Стабильность не задана ни для одного пункта; наименее стабильны пункты с неподтверждёнными допущениями.

### Уникальность и актуальность {#uniqueness}

1. ID уникальны, `H` и `Q` оформлены по глоссарию.
2. Остались «Проверка 123.» в описании F-PT, висящие ссылки `[123]`, `[glossary]`, пометки «(допущение)» в
   таблицах `DR-PT-CREATE-001` при принятом `H01`, устаревшие допущения в uc.md.

## Кандидаты в общие требования {#common-candidates}

### Глобальный уровень {#common-global}

Дизайн-система утверждает, что все справочники устроены одинаково, поэтому общие механизмы выгодно описать один раз.

| Кандидат | Что забрать | Откуда |
| :--- | :--- | :--- |
| `SF-G-PAG`, `SF-G-SORT`, `SF-G-FILTER` | Пагинация, сортировка, фильтры, чипы, поиск | `FR-PT-LIST-005`…`007` |
| `SF-G-TOAST` (заполнить) | Тексты «Готово» и «Ошибка», время показа, `data-testid` | Ссылки из всех SF |
| `SF-G-LOCK` | Проверка одновременного изменения, ответ `RECORD_MODIFIED` | `DR-PT-UPDATE-001`, `FR-PT-UPDATE-003` |
| `SF-G-SESSION` | Поведение при ответе `401` | `FR-PT-LIST-005.H03` |
| Глобальный AR | Порядок проверок, коды ошибок, `null` и пустые параметры, форматы, эталоны 401/403/500 | FR отказа |
| Глобальные NFR | Тестовый стенд и способ замера, WCAG 2.1 AA, журнал аудита, часовой пояс показа | Все FR |
| Глобальный UI | Правила `data-testid`, поведение модального окна, состояния таблицы | `FR-PT-LIST-005`, `UI-PT-001` |
| SR и роли | Браузеры, минимальная ширина 1280px, справочник ролей | Дизайн-система; роли не описаны |

### Уровень основной функциональности {#common-feature}

1. `DR-PT-001` — сущность `dict_product_type` целиком; DR детальных функциональностей ссылаются на неё.
2. Правила проверки полей — одна таблица для `FR-PT-CREATE-002`, `FR-PT-UPDATE-002`, `UI-PT-001` и фильтров
   `FR-PT-LIST-004`.
3. `AR-PT-001` — общая схема записи `product-type.schema.json` для ответов READ, UPDATE, LIST и CREATE.
4. Тестовый набор `AR-PT-LIST-001.fixture.json` — на уровень F, потому что им пользуются все SF.
5. События аудита справочника: создание, изменение, смена статуса, удаление.
