# Термины методологии {#glossary}

## Обзор {#overview}

В статье собраны термины, которыми описана организация требований: уровни (продукт, основная и детальная
функциональность), типы требований, их части и правила идентификации. Эти термины не зависят от продукта и одинаково
применяются в любом проекте, который ведётся по данной методологии. Сами правила записи и именования требований
приведены в статье [Стандарт создания требований к ПО][1], а термины предметной области продукта — в [Глоссарии][2].

Каждый термин описан в отдельном подразделе и содержит определение, понятное без чтения остальных подразделов. Термины 
расположены по алфавиту: сначала названия на латинице (A–Z), затем на кириллице (А–Я). 

Фиксация терминов методологии помогает проекту:

- **Говорить на одном языке:** Аналитики, разработчики и тестировщики одинаково понимают, что такое основная и детальная
функциональность, сценарий, критерий приёмки.
- **Находить место требования:** По названию типа и уровня сразу ясно, где записать требование и как построить его ID.
- **Ссылаться на определения:** У каждого термина есть якорь, поэтому из требований и статей на него ведут ссылки с
предпросмотром.
- **Быстрее вводить новичков:** Новый участник проекта читает короткие определения, не изучая стандарт целиком.

## Термины {#terms}

### ID требования {#requirement-id}

Уникальный идентификатор пункта в формате `ТИП-ОБЛАСТЬ-НОМЕР`: тип требования, область (пусто для глобального уровня,
код основной функциональности, код основной и детальной либо `G` с кодом глобальной детальной) и трёхзначный номер.
Примеры: `BR-028`, `BR-COUNTRY-001`, `FR-COUNTRY-CREATE-001`, `FR-G-PAG-001`. Номер не переиспользуется: устаревшее
требование получает статус `retired` и остаётся в списке.

### Бизнес-правило (BR, Business Rule) {#br}

Правило предметной области, которому должны подчиняться продукт и его данные. Записывается на глобальном уровне и на
уровне основной функциональности. На уровне детальной функциональности встраивается в функциональное требование как
условие. Примеры ID: `BR-028`, `BR-COUNTRY-001`.

### Бизнес-цель (BG, Business Goal) {#bg}

Цель бизнеса, ради которой создаются функциональности продукта. Записывается на глобальном уровне. На уровне основной
функциональность ссылается на цели в своём паспорте атрибутом `Цели`. Пример ID: `BG-001`. У основных функциональностей 
так же есть бизнес-цель - зачем бизнесу нужна функциональность. Пример ID: `BG-COUNTRY-001`. 

### Владелец требования {#owner}

Уровень, которому принадлежит требование: самый нижний, на котором оно истинно целиком. Определяется вопросом «К
скольким детальным функциональностям это относится?»: к одной — владелец она, к нескольким одной основной — основная
функциональность, к нескольким основным — глобальный уровень. Уровень владельца читается из ID. Правило исключает
двойной счёт требований в статистике.

### Внешний интерфейс (EI, External Interface) {#ei}

Требование к обмену функциональности с внешней системой: что она получает или отдаёт, протокол, порядок обмена, повторы,
реакция на сбои. Для внешней системы заводится проектное ограничение с владельцем, а её контракт хранится рядом с
пакетом. Записывается на глобальном уровне и на уровне основной функциональности. Примеры ID: `EI-001`,
`EI-COUNTRY-001`.

### Вопрос (Q, Question) {#question}

Нерешённый вопрос по пункту или по всей функциональности. Статусы: `открыт`, `закрыт`. Обязательный атрибут — `Решает`,
а у закрытого вопроса ещё и `Решение` (что решено и когда). Закрытый вопрос остаётся в пункте как история решения.
Пример ID: `FR-COUNTRY-UPDATE-001.Q01`.

### Глобальная детальная функциональность (SF-G) {#global-sub-feature}

Детальная функциональность, которая применяется во многих основных функциональностях: пагинация, сортировка, фильтр,
всплывающие сообщения, формат ошибок, блокировка. У неё нет предметного родителя, поэтому вместо кода основной
функциональности стоит зарезервированный код `G`. Она целиком описывает своё поведение (требования, интерфейс, API,
приёмку), а основная функциональность подключает её атрибутом `Применяется` и не описывает заново. Пример ID:
`SF-G-PAG`.

### Глобальное требование {#global-requirement}

Требование, которое относится к нескольким основным функциональностям сразу (например, формат даты и времени).
Записывается на глобальном уровне и действует на все функциональности без явной ссылки. Функциональность ссылается на
него только там, где её пункт на него опирается, и ничего не копирует. Пример ID: `DR-001`.

### Глобальный уровень (продукт) {#global-level}

Верхний уровень структуры требований: на нём записаны требования, которые действуют на весь продукт и относятся сразу к
нескольким основным функциональностям, а также глобальные детальные функциональности. У ID таких требований нет кода
функциональности: `BR-028`, `NFR-001`.

### Детальная функциональность (SF, Sub-Feature) {#sub-feature}

Часть основной функциональности со своим поведением, которое можно описать и проверить отдельно: создание, импорт,
список. У неё свои функциональные требования, API и критерии приёмки. Приоритет и статус детальной функциональности
можно задать отдельно, а приём основной функциональности идёт целиком. Глубина ровно два уровня: детальная
функциональность внутри детальной не бывает. Вкладки, кнопки и разделы меню детальными функциональностями не являются,
это интерфейс. Пример ID: `SF-COUNTRY-CREATE`.

### Допущение (H, Hypothesis) {#hypothesis}

Принятое решение, которое ещё не подтвердил владелец решения. Записывается внутри пункта, к которому относится, а если
касается всей функциональности — в разделе допущений и открытых вопросов её обзора. Статусы: `принято`, `подтверждено`,
`отвергнуто`. Обязательный атрибут — `Подтверждает`. Пример ID: `FR-COUNTRY-LIST-003.H01`.

### Интерфейсное требование (UI, User Interface) {#ui}

Описание экрана, диалога или компонента с макетом: элементы, порядок, состояния, события и сообщения. Один экран — один
пункт. Если экран общий для нескольких детальных функциональностей, пункт записывается на уровне основной
функциональности. Общие токены и правила доступности и адаптивности записаны один раз в глобальном пункте `UI-001`,
экран ссылается на него. Примеры ID: `UI-COUNTRY-001`, `UI-COUNTRY-LIST-001`, `UI-G-TOAST-001`.

### Критерий приёмки (AC, Acceptance Criterion) {#ac}

Сценарий приёмки на языке Gherkin, который проверяет выполнение требования. Критерий связывается с проверяемыми пунктами
тегами (`@FR-…`, `@UC-…`, `@UI-…`, `@DR-…`), а область его ID определяется этими тегами. Критерии записываются в файл
`07-acceptance.feature`. Проверка, которую нельзя автоматизировать, помечается тегом `@manual`. Примеры ID:
`AC-COUNTRY-001`, `AC-COUNTRY-CREATE-001`, `AC-G-PAG-001`.

### Нефункциональное требование (NFR, Non-Functional Requirement) {#nfr}

Требование к характеристике качества продукта. Записывается на глобальном уровне и на уровне основной функциональности.
На уровне детальной функциональности встраивается в функциональное требование, если у него нет собственного показателя и
способа проверки. Если есть (например, время ответа списка с 95-м процентилем и условиями измерения), оформляется
отдельным пунктом. Примеры ID: `NFR-001`, `NFR-COUNTRY-001`.

### Основная функциональность (F, Feature) {#feature}

Пункт меню продукта, который заказчик принимает и приоритизирует целиком, например «Справочник стран» или «Накладные».
Одна основная функциональность соответствует одной спецификации. Отдельного уровня «модуль» нет: группа меню
(«Справочники») записывается атрибутом `group` и нужна только для свёртки статистики. Чтобы проверить, что это основная
функциональность, задают вопрос: «Заказчик примет это отдельно от остального?» Пример ID: `F-COUNTRY`.

### Пакет требований {#requirements-package}

Папка основной функциональности, в которой требования разложены по слоям (обзор, бизнес, сценарии, интерфейс, функции,
данные, API, внешние интерфейсы, качество, тесты) и по файлам. Сначала в каждом слое идёт раздел общего для
функциональности (уровень F), затем по разделу на каждую детальную функциональность. Детальная функциональность может
иметь собственную подпапку в пакете.

### Проектное ограничение (CON, Constraint) {#con}

Ограничение, которое проект принимает как данность и в рамках которого создаётся продукт. Записывается на глобальном
уровне. На уровне основной функциональности допускается как исключение, только если ограничение касается одной
функциональности (например, внешней системы). Примеры ID: `CON-001`, `CON-COUNTRY-001`.

### Системное требование (SR, System Requirement) {#sr}

Требование к среде работы продукта: серверная среда, операционная система, поддерживаемые браузеры. Записывается только
на глобальном уровне. Пример ID: `SR-001`.

### Событие экрана (U) {#ui-event}

Часть интерфейсного требования: действие пользователя или системы на экране вместе с условием, реакцией и результатом.
Нумерация сквозная внутри интерфейсного пункта. Пример ID: `UI-COUNTRY-LIST-001.U03`.

### Сообщение интерфейса (MSG) {#msg}

Текст, который система показывает пользователю. Описывается в составе интерфейсного пункта и идентифицируется не
номером, а ключом локализации, который уникален во всём продукте. Пример ID: `MSG:country.deleted`.

### Состояние экрана (S) {#ui-state}

Часть интерфейсного требования: вид экрана в конкретной ситуации, например «Пустой результат», «Загрузка», «Ошибка
загрузки». Состояния описываются одной таблицей и остаются частью экрана: они показывают те же элементы по-разному и
отдельно не принимаются. Отдельный интерфейсный пункт нужен, только если «состояние» на деле другой экран со своим
составом элементов (диалог удаления, форма). Пример ID: `UI-COUNTRY-LIST-001.S02`.

### Спецификация (SPEC) {#spec}

Документ с полным набором требований одной основной функциональности: от целей и сценариев до API, данных и критериев
приёмки. Одна основная функциональность соответствует одной спецификации. Пример ID: `SPEC-COUNTRY-V0.1`.

### Сценарий (UC, Use Case) {#uc}

Описание того, зачем пользователь выполняет действие: цель, актор, основной поток, альтернативы, предусловие и
постусловие. Принадлежит основной функциональности и ссылается атрибутом `Использует` на детальные функциональности,
которые задействует. Один сценарий может использовать несколько детальных функциональностей, а одна детальная
функциональность может входить в несколько сценариев. Сценария уровня детальной функциональности не бывает. Пример ID:
`UC-COUNTRY-001`.

### Требование к API (AR, API Requirement) {#ar}

Описание операции API с атрибутами (метод и путь, роли, тело запроса, параметры, ответы, примеры) и общих правил API.
Записывается на всех трёх уровнях: операция одной детальной функциональности — на уровне детальной функциональности,
операция для нескольких — на уровне основной функциональности, правила для всех функциональностей — на глобальном
уровне. Примеры ID: `AR-001`, `AR-COUNTRY-LIST-001`, `AR-COUNTRY-004`.

### Требование к данным (DR, Data Requirement) {#dr}

Описание данных: состав полей сущности, типы, ограничения, уникальность. Поля записываются таблицей в одном месте, и она
служит единым источником состава данных для схемы данных, БД и API. Поэтому требование к данным уровня детальной
функциональности всегда оформляется отдельным пунктом. Примеры ID: `DR-001`, `DR-COUNTRY-001`, `DR-COUNTRY-UPDATE-001`.

### Функциональное требование (FR, Functional Requirement) {#fr}

Описание того, что делает система, например «Система показывает список накладных выбранного направления». Проверяется
через API и критерии приёмки. Если убрать интерфейс и оставить API, функциональное требование останется. На глобальном
уровне встречается только внутри глобальной детальной функциональности. Примеры ID: `FR-COUNTRY-001`,
`FR-COUNTRY-CREATE-001`, `FR-G-PAG-001`.

### Элемент экрана (E) {#ui-element}

Часть интерфейсного требования: кнопка, поле, таблица или другой элемент экрана. Отдельным владельцем не является, но
может ссылаться на функциональные требования других детальных функциональностей (кнопка «Добавить» на экране списка
ссылается на создание). Пример ID: `UI-COUNTRY-LIST-001.E04`.
