# Стандарт создания требований для ИИ-разработки и спринтов {#ai-spec-driven-standard}

## Обзор {#overview}

Стандарт адаптирует классическую иерархию требований под скоростную разработку спринтами с использованием ИИ-агентов
(Cursor, Copilot, LLM) и подготовку приёмочной документации для Заказчика. Главный принцип стандарта — **единый источник
истины (Single Source of Truth)** без дублирования одного и того же факта в разных документах.

## Матрица оптимизации сущностей {#entity-optimization}

Вместо 14 разрозненных типов требований оставляются **7 ключевых сущностей** (`F`, `SF`, `UC`, `DR`, `FR`, `AR`, `AC`),
а также глобальные функциональности (`SF-G-*`), единая дизайн-система (`design-system/`) и точечно выносимые `UI` и
`NFR`.

| Оставляем | Что вливаем внутрь и убираем как отдельные типы | Обоснование для ИИ и спринтов |
| :--- | :--- | :--- |
| **F и SF** | — | Каркас для декомпозиции бэклога по спринтам (`must` / `should`) и поэтапной сдачи Заказчику. |
| **SF-G-*** | Глобальные `FR`, `AR`, `UI`, `AC` | Переиспользуемые механизмы (пагинация, сортировка, тосты, блокировки `SF-G-LOCK`), описанные один раз. |
| **UC** (Уровень F) | `BG` (бизнес-цель), `CON` (ограничения) | UI-независимые сценарии для согласования с Заказчиком, руководства пользователя и генерации E2E-тестов. |
| **DR** (Уровень F) | `BR` про данные (уникальность, статусы) | Единая таблица сущности, индексы и машина состояний для генерации миграций БД и моделей бэкенда. |
| **FR** (Уровень F и SF) | `BR` (логика), `EI` (интеграции), `UI` (для одной SF), операционные `NFR` (лимиты), `AC` (Gherkin) | Самодостаточная спецификация: бизнес-логика, валидации, поля формы и сценарии приёмки в одном месте. |
| **AR** (Уровень F и SF) | Общие правила API и точечные `AC` | Контракт API (метод, URL, DTO, коды ошибок) для генерации OpenAPI/Swagger, контроллеров и клиентов. |
| **UI** (Уровень F) | User Flow, общие экраны и экранные `AC` | Выносится только если один экран объединяет несколько `SF` (например, список или карточка). |
| **NFR** (Уровень F) | Системные и инфраструктурные требования | Только требования, не сводимые к `AC` (сроки хранения данных, права СУБД, нагрузка, отказоустойчивость). |
| **Design System** | `brandbook.md` и `ui-kit.md` | Визуальный стандарт: бренд-бук для людей и реестр компонентов UI-кита (Слой 3) для генерации фронтенда. |

## Симметричная структура каталогов под Zensical {#directory-structure}

Документация организуется симметрично для уровня основной функциональности (`f/`) и каждой детальной функциональности
(`sf-*/`). Вспомогательные файлы (`fr.md`, `ar.md`, `dr.md` и др.) подключаются во вкладки `index.md` через инклуды
(`--8<--`).

```text
docs/requirements/
├── _global/                              # Глобальные требования и стандарты продукта
│   ├── design-system/                    # Единая папка визуальных стандартов (Дизайн-система)
│   │   ├── brandbook.md                  # Бренд-бук (логотипы, цвета, типографика, Tone of Voice)
│   │   └── ui-kit.md                     # Технический UI-кит и дизайн-токены (Слой 3 для ИИ)
│   ├── sf-g-pag/                         # Глобальная пагинация (index.md, fr.md, ar.md, ui.md)
│   ├── sf-g-sort/                        # Глобальная сортировка
│   ├── sf-g-filter/                      # Глобальная фильтрация
│   ├── sf-g-toast/                       # Глобальные уведомления
│   └── sf-g-lock/                        # Глобальная оптимистичная блокировка
│
└── country/                              # Модуль основной функциональности F-COUNTRY
    ├── f/                                # Уровень F-COUNTRY (пункт меню «Общие»)
    │   ├── index.md                      # Карточка F-COUNTRY и сборка вкладок (CONTEXT..UI)
    │   ├── context.md                    # Вкладка CONTEXT: глоссарий, бизнес-цель, границы, матрица ролей
    │   ├── uc.md                         # Вкладка UC: UI-независимые сценарии (UC-COUNTRY-001..007)
    │   ├── dr.md                         # Вкладка DR: таблицы БД, индексы, State Machine (PlantUML)
    │   ├── fr.md                         # Вкладка FR: общие требования уровня F + сквозные AC
    │   ├── ar.md                         # Вкладка AR: общие правила API, заголовки, базовые коды ошибок
    │   ├── nfr.md                        # Вкладка NFR: системные требования (сроки хранения, аудит в БД)
    │   └── ui.md                         # Вкладка UI: User Flow (PlantUML), общие экраны + экранные AC
    │
    ├── sf-list/                          # SF-COUNTRY-LIST (пункт меню «Список и поиск»)
    │   ├── index.md                      # Карточка SF и сборка вкладок (FR | AR)
    │   ├── fr.md                         # Логика списка, поиска, фильтрации + вложенные AC
    │   └── ar.md                         # Контракт GET /api/v1/countries
    │
    ├── sf-read/                          # SF-COUNTRY-READ (пункт меню «Карточка страны»)
    │   ├── index.md                      # Карточка SF и сборка вкладок (FR | AR)
    │   ├── fr.md                         # Логика чтения атрибутов и метаданных + вложенные AC
    │   └── ar.md                         # Контракт GET /api/v1/countries/{id}
    │
    ├── sf-create/                        # SF-COUNTRY-CREATE (пункт меню «Создание»)
    │   ├── index.md                      # Карточка SF и сборка вкладок (FR | AR)
    │   ├── fr.md                         # Форма создания, валидации ISO 3166-1, уникальность + AC
    │   └── ar.md                         # Контракт POST /api/v1/countries
    │
    ├── sf-update/                        # SF-COUNTRY-UPDATE (пункт меню «Редактирование»)
    │   ├── index.md                      # Карточка SF и сборка вкладок (FR | AR)
    │   ├── fr.md                         # Логика изменения названий, блокировка кодов, SF-G-LOCK + AC
    │   └── ar.md                         # Контракт PATCH /api/v1/countries/{id}
    │
    ├── sf-activation/                    # SF-COUNTRY-ACTIVATION (пункт меню «Активация и деактивация»)
    │   ├── index.md                      # Карточка SF и сборка вкладок (FR | AR)
    │   ├── fr.md                         # Смена статуса активности, проверка версии + вложенные AC
    │   └── ar.md                         # Контракт POST /api/v1/countries/{id}/activate (и deactivate)
    │
    ├── sf-delete/                        # SF-COUNTRY-DELETE (пункт меню «Удаление»)
    │   ├── index.md                      # Карточка SF и сборка вкладок (FR | AR)
    │   ├── fr.md                         # Проверка ссылок в подсистемах, логическое удаление + AC
    │   └── ar.md                         # Контракт DELETE /api/v1/countries/{id}
    │
    └── sf-import/                        # SF-COUNTRY-IMPORT (пункт меню «Импорт из НСИ АСФР»)
        ├── index.md                      # Карточка SF и сборка вкладок (FR | AR)
        ├── fr.md                         # Sequence-схема, фоновая загрузка, расхождения, транзакция + AC
        └── ar.md                         # Контракты запуска, статуса, предпросмотра и применения импорта
```

## Разграничение нефункциональных требований (NFR) {#nfr-rules}

Чтобы не создавать лишних сущностей, нефункциональные требования разделяются по способу их проверки:

1. **Операционные `NFR` → встраиваются в `FR` / `UI` и проверяются через `AC`:**
   * Время отклика конкретной операции (например, загрузка списка не более 500 мс при объёме до 500 записей).
   * Лимиты на размер загружаемого файла или пакета данных при импорте.
   * Транзакционность записи в журнал аудита при выполнении бизнес-действия.
2. **Системные и инфраструктурные `NFR` → остаются в `f/nfr.md`:**
   * Сроки хранения и ротация данных (Retention policy, например хранение логов и отчётов импорта 12 месяцев).
   * Ограничения уровня СУБД и безопасности (запрет `UPDATE` и `DELETE` на уровне прав ролей БД для таблицы аудита).
   * Нагрузочные профили (выдерживание N одновременных запросов без деградации, проверяется k6/JMeter).
   * Отказоустойчивость и политики повторов (retry с экспоненциальной задержкой при недоступности внешней системы).

## Правила встраивания критериев приёмки (AC) {#ac-embedding}

Отдельные файлы `ac.md` не создаются. Критерии приёмки в формате Gherkin оформляются как завершающий подраздел (`####
Критерии приёмки (AC)`) непосредственно внутри проверяемого требования:

* **В `fr.md` (обязательно):** Сценарии проверки бизнес-логики, валидаций, прав доступа, транзакций и сохранения в БД
  (основа для интеграционных и API-тестов).
* **В `ui.md` (обязательно):** Сценарии проверки поведения интерфейса, видимости элементов, блокировки кнопок, тостов и
  переходов между экранами (основа для E2E/UI-тестов).
* **В `ar.md` (точечно):** Добавляется только для чисто технических нюансов протокола (Rate Limiting, проверка подписи
  вебхуков, специфические заголовки или правила сериализации), не описанных в `fr.md`.

## Правила размещения схем (PlantUML) {#diagrams}

Диаграммы хранятся в текстовом виде (PlantUML) внутри соответствующих файлов, чтобы ИИ-агенты могли парсить их напрямую:

* **ER-диаграммы и диаграммы состояний (State Machine):** Размещаются в `f/dr.md` рядом с описанием таблиц и переходов
  статусов сущности.
* **Диаграммы последовательности (Sequence Diagram):** Размещаются в начале `sf-*/fr.md` для сложных асинхронных процессов, фоновых
  задач и внешних интеграций (например, `sf-import/fr.md`).
* **User Flow (диаграмма активности или состояний):** Размещаются в начале `f/ui.md` для отображения роутинга, разделения по ролям, границ
  модальных окон и точек возврата.

## Полный ИИ-пайплайн разработки по слоям {#ai-pipeline}

Чтобы ИИ-агенты генерировали код без галлюцинаций, контекст передаётся поэтапно — от абстрактного поведения к жёстким
техническим контрактам и визуальному слою.

### Четыре слоя подачи контекста в промпт

1. **Слой 1. Поведение и границы (`F` + `UC`):** Задаёт бизнес-смысл, порядок шагов пользователя и обработку краевых
   случаев без привязки к реализации (`f/context.md`, `f/uc.md`).
2. **Слой 2. Контракты и логика (`DR` + `SF-G` + `SF` [`FR` + `AR` + `AC`] + `NFR`):** Задаёт структуру БД, глобальные
   правила (`_global/sf-g-*`), логику конкретной фичи, эндпоинты API, критерии приёмки и системные ограничения.
3. **Слой 3. Визуал (`UI` + `UI-Kit`):** Задаёт композицию общих экранов (`f/ui.md`) и привязку к готовым компонентам и
   дизайн-токенам проекта (`_global/design-system/ui-kit.md`). Файл `brandbook.md` в промпт кодогенерации не передаётся,
   так как его правила уже зашиты в токены UI-кита.
4. **Слой 4. Верификация (`AC` внутри `FR` и `UI`):** Используется ИИ-агентом для генерации автотестов и самопроверки
   написанного кода.

### Матрица генерации артефактов для ИИ-агента

| Этап разработки | Какие файлы передаём в контекст ИИ | Что генерирует ИИ-агент |
| :--- | :--- | :--- |
| **1. Проектирование БД и аудита** | `f/dr.md` + `f/nfr.md` | SQL-миграции, таблицы, частичные индексы, ORM-модели, права доступа СУБД и фоновые задачи ротации данных. |
| **2. Глобальный каркас** | `_global/sf-g-*/` (`fr.md`, `ar.md`, `ui.md`) | Базовые middleware (ошибки, оптимистичная блокировка), общие DTO пагинации/сортировки и базовые UI-обёртки. |
| **3. Бэкенд-логика и API** | `f/context.md` + `f/dr.md` + `f/ar.md` + `sf-*/fr.md` + `sf-*/ar.md` | Контроллеры API, DTO, сервисный слой с бизнес-логикой, валидациями, транзакциями аудита и OpenAPI-схема. |
| **4. Фронтенд и экраны** | `f/uc.md` + `f/ui.md` + `sf-*/fr.md` + `sf-*/ar.md` + `_global/design-system/ui-kit.md` | Роутинг, сторы (state management), страницы, модальные окна, формы с валидацией и интеграция с API на компонентах UI-кита. |
| **5. Автотесты и приёмка** | `f/uc.md` + `AC` из `sf-*/fr.md` + `AC` из `f/ui.md` | Модульные и интеграционные тесты API (по `AC` из `FR`), сквозные E2E-тесты Playwright/Cypress (по `AC` из `UI` и `UC`). |
