# Стандарт создания требований к ПО {#standard-requirements}

## Обзор {#overview}

Стандарт отвечает на один вопрос аналитика: куда записать требование и как его назвать. Правила одинаковы для любой 
функциональности. 

## Типы требований {#types}

В таблице перечислены все типы требований продукта. Для каждого типа указаны префикс, расшифровка и вид ID на трёх 
уровнях: глобальном, уровне основной функциональности (F) и уровне детальной функциональности (SF). ID строится по схеме 
`ТИП-ОБЛАСТЬ-НОМЕР`: у глобального требования области нет (`BR-028`), у требования уровня F в области стоит код 
функциональности (`BR-COUNTRY-001`), у требования уровня SF — коды функциональности и детальной функциональности 
(`FR-COUNTRY-CREATE-001`). «Нет» в ячейке означает, что требование этого типа на данном уровне не записывается, 
«встраивается в FR» — что оно оформляется условием внутри функционального требования. Код `COUNTRY` в примерах — код 
основной функциональности «Справочник стран».

| Префикс | Расшифровка | Глобальный | Уровень F | Уровень SF |
|---|---|---|---|---|
| **BG** | Business Goal, бизнес-цель | `BG-001` | `BG-COUNTRY-001` | нет |
| **CON** | Constraint, проектное ограничение | `CON-001` | `CON-COUNTRY-001` (только если ограничение касается одной F) | нет |
| **BR** | Business Rule, бизнес-правило | `BR-028` | `BR-COUNTRY-001` | встраивается в FR, DR |
| **F** | Feature, основная функциональность | нет | `F-COUNTRY` | нет |
| **SF** | Sub-Feature, детальная функциональность | `SF-G-PAG` | нет | `SF-COUNTRY-CREATE` |
| **UC** | Use Case, сценарий достижения цели | нет | `UC-COUNTRY-001` | нет |
| **FR** | Functional Requirement, функциональное требование | `FR-G-PAG-001` (только внутри глобальной SF) | `FR-COUNTRY-001` | `FR-COUNTRY-CREATE-001` |
| **NFR** | Non-Functional Requirement, характеристика качества | `NFR-001` | `NFR-COUNTRY-001` | встраивается в FR или отдельно, если есть собственный показатель |
| **DR** | Data Requirement, требование к данным | `DR-001` | `DR-COUNTRY-001` | `DR-COUNTRY-UPDATE-001` (всегда отдельно) |
| **AR** | API Requirement, требование к API: операция и правила API | `AR-001` | `AR-COUNTRY-001` | `AR-COUNTRY-LIST-001` |
| **EI** | External Interface, интерфейс с внешней системой | `EI-001` | `EI-COUNTRY-001` | нет |
| **SR** | System Requirement, среда, ОС, браузеры | `SR-001` | нет | нет |
| **UI** | User Interface, описание экрана или диалога с макетом | `UI-G-TOAST-001` (в глобальной SF) | `UI-COUNTRY-001` (экран общий для нескольких SF) | `UI-COUNTRY-LIST-001` |
| **AC** | Acceptance Criterion, сценарий приёмки (Gherkin) | `AC-G-PAG-001` | `AC-COUNTRY-001` (сквозная проверка UC) | `AC-COUNTRY-CREATE-001` |

## Уровни требований {#levels}

Требования образуют иерархию из трёх уровней: продукт (глобальный уровень), основная функциональность (F) и детальная 
функциональность (SF). Каждое требование записывается на самом нижнем уровне, на котором оно истинно целиком: относится 
к одной SF — на уровне SF, к нескольким SF одной F — на уровне F, к нескольким F — на глобальном уровне. Схема ниже 
показывает, какие типы требований допустимы на каждом уровне, а список под ней описывает каждый вид требований.

```
ПРОДУКТ (глобальный уровень)
 ├─ Глобальные требования: BG, CON, BR, NFR, DR, AR, EI, SR     BR-028, NFR-001
 ├─ Глобальные детальные функциональности (SF-G-…)               SF-G-PAG, SF-G-SORT, SF-G-FILTER, SF-G-TOAST
 │    └─ их FR, UI, AC                                           FR-G-PAG-001
 │
 └─ ОСНОВНАЯ ФУНКЦИОНАЛЬНОСТЬ  F-…  =  СПЕЦИФИКАЦИЯ  SPEC-…      F-COUNTRY
      │   Требования уровня F: BG, BR, NFR, DR, AR, EI, CON, UC, FR, UI, AC
      └─ ДЕТАЛЬНАЯ ФУНКЦИОНАЛЬНОСТЬ  SF-…                         SF-COUNTRY-CREATE
            Требования уровня SF: FR, DR, AR, UI, AC (BR и NFR как правило встраиваются)
```

- **Бизнес-цель (Business Goal, BG)**: Зачем бизнесу нужен продукт: цель, ради которой создаются функциональности. 
Записывается только на глобальном уровне. У основных функциональностей так же есть бизнес-цель - зачем бизнесу нужна 
функциональность. 

- **Проектное ограничение (Constraint, CON)**: Ограничение, которое проект принимает как данность и в рамках которого 
создаётся продукт. Записывается на глобальном уровне. На уровне F допускается только если ограничение касается одной 
функциональности (например, внешней системы), на уровне SF не бывает.

- **Бизнес-правило (Business Rule, BR)**: Правило предметной области, которому подчиняются продукт и его данные. 
Записывается на глобальном уровне и на уровне F. На уровне SF встраивается в FR как условие, встраивается в DR.

- **Основная функциональность (F, Feature)**: Функциональность продукта, которую заказчик принимает целиком 
(«Справочник стран», «Накладные»). Не «Удаление страны» (отдельно не примет), а «Управление справочником стран».

- **Детальная функциональность (SF, Sub-Feature)**: Часть основной функциональности со своим поведением, которое можно 
описать и проверить отдельно (создание, импорт, список). Приоритет и статус каждой SF можно задать отдельно (импорт 
`should`, остальное `must`) - заказчик может принять на промежуточных этапах целиком одну или несколько SF.

- **Глобальная детальная функциональность (SF-G-…)**: SF, которая применяется во многих F (пагинация, тосты, формат 
ошибок, блокировка). У неё нет предметного родителя, поэтому код основной функциональности зарезервирован как `G`.

- **Сценарий (Use Case, UC)**: Зачем пользователь это делает: цель, шаги, альтернативы. Принадлежит F и ссылается на SF, 
которые использует. UC уровня SF не бывает. Один UC может использовать несколько SF, одна SF — быть в нескольких UC.

- **Функциональное требование (FR, Functional Requirement)**: Что делает система: «Система показывает список накладных 
выбранного направления». Проверяется через API и AC.

- **Нефункциональное требование (Non-Functional Requirement, NFR)**: Характеристика качества продукта. Записывается на 
глобальном уровне и на уровне F. На уровне SF встраивается в FR, а отдельным пунктом оформляется, только если у него 
есть собственный показатель и способ проверки (например, время ответа списка).

- **Требование к данным (Data Requirement, DR)**: Какие данные хранит система: состав полей сущности, типы, ограничения, 
уникальность. Поля записываются таблицей в одном месте, из неё строятся схема данных, таблицы БД и модели API. 
На уровне SF записывается всегда отдельным пунктом.

- **Требование к API (API Requirement, AR)**: Операция API с её атрибутами (метод и путь, роли, параметры, ответы) и 
общие правила API. Записывается на всех трёх уровнях: операция одной SF — на уровне SF, операция для нескольких SF и 
общие правила функциональности — на уровне F, правила для всех функциональностей — на глобальном уровне.

- **Внешний интерфейс (External Interface, EI)**: Как функциональность обменивается данными с внешней системой: что 
получает или отдаёт, протокол, порядок обмена, повторы, реакция на сбои. Записывается на глобальном уровне и на уровне 
F, на уровне SF не бывает.

- **Системное требование (System Requirement, SR)**: Среда, в которой работает продукт: операционная система, браузеры. 
Записывается только на глобальном уровне.

- **Интерфейсное требование (User Interface, UI)**:  Как это выглядит и работает на экране: вкладки, порядок, состояния. 
Каждый элемент ссылается на FR, который реализует. Если убрать интерфейс и оставить API, FR останется, а UI исчезнет.

- **Критерий приёмки (Acceptance Criterion, AC)**: Сценарий на языке Gherkin, по которому проверяют, что требование 
выполнено. Связывается с проверяемыми требованиями тегами (`@FR-…`, `@UC-…`, `@UI-…`, `@DR-…`). Записывается на всех 
трёх уровнях: сквозная проверка UC принадлежит уровню F, проверка одной SF — уровню SF, проверка глобальной SF — 
глобальному уровню.

## Описание и связи основной функциональности {#f-links}

На уровне основной и детальной функциональности назначение записывается одним атрибутом `Описание` по формуле
«пользователь делает X, чтобы получить Y». Отдельных атрибутов «бизнес-цель» и «проблема» на этих уровнях нет: проблему
и цель хранит BG, а причину существования детальной функциональности показывают сценарии, которые её используют.

Паспорт основной функциональности связывает её с целями продукта и с глобальными детальными функциональностями двумя
атрибутами.

| Атрибут | Значение | Правило |
|---|---|---|
| `Относится` | Один или несколько BG, например `BG-001` | Обязателен: без него функциональность не связана с целью продукта |
| `Использует` | Глобальные SF (`SF-G-…`), которые функциональность подключает | Пишется, только если есть подключаемые глобальные SF. Пустой атрибут не оставляют |

Подключённая глобальная SF не описывается заново: её поведение берётся из её собственного описания.

## Допустимые упрощения {#simplifications}

Полная форма стандарта нужна, когда требований много, а потребителей у них несколько: заказчик, разработчики, 
тестировщики и ИИ-агенты. Если времени на полную форму не хватает, допускаются упрощения, но только при трёх условиях:

- упрощение перечислено в таблице ниже, других упрощений нет;
- у каждого упрощения есть условие возврата к полной форме;
- упрощение меняет только оформление: тип, уровень и владелец требования остаются прежними, поэтому позже его можно 
развернуть без переписывания смысла.

| Тип | Упрощённая форма | Когда вернуть полную форму |
|---|---|---|
| **BR** | Правило записывается условием внутри FR. Правило о данных (уникальность, допустимые статусы, переходы) записывается ограничением в DR. Отдельного ID у правила нет | Правило понадобилось во втором FR или SF, либо заказчик согласует его отдельно. Тогда оно выносится строкой в таблицу «Бизнес-правила» с ID, а FR ссылаются на него |
| **EI** | Обмен с внешней системой описывается внутри FR той SF, которая его использует | Одну внешнюю систему использует несколько SF. Тогда заводится EI уровня F |
| **UI** | Экран одной SF описывается внутри её FR: поля формы, состояния, сообщения. Отдельного UI-пункта нет | Экран общий для нескольких SF, либо у экрана появился макет с элементами, событиями и состояниями, которые проверяются приёмкой отдельно |
| **NFR** | Операционные требования (время отклика операции, лимиты) записываются условием в FR и проверяются через AC | У требования есть собственный показатель и способ проверки не через AC (нагрузка, сроки хранения данных) |

Упрощение BR, EI, UI и NFR сокращает число пунктов, но не отменяет правило владельца: общее для нескольких SF 
требование не копируется в каждую SF, а записывается один раз уровнем выше.

## Последовательность работ и состав пакета {#authoring-order}

Работа идёт от общего к частному, и каждый этап опирается на результат предыдущих. В таблице для каждого этапа
указано, что записывается, что получает ИИ-агент в контекст и что он создаёт. Визуальный и технический стандарты
относятся к глобальному уровню и создаются один раз на продукт, до описания экранов и написания кода.

| № | Этап | Записывается | ИИ получает в контекст | ИИ создаёт |
|---|---|---|---|---|
| 1 | Цель и границы функциональности | BG, CON, роли, каталог SF, UC (аналитик) | — (результат согласуется с заказчиком и входит в контекст следующих этапов) | — |
| 2 | Визуальный стандарт (глобально, один раз) | Бренд-бук: логотипы, цвета, типографика, тон коммуникации. UI-kit: компоненты и дизайн-токены (дизайнер, аналитик) | UI-kit. Бренд-бук ИИ не передаётся: его правила уже заложены в токены UI-kit | Тему фронтенда: токены и базовые компоненты |
| 3 | Технический стандарт (глобально, один раз) | Архитектура и правила кодирования: стек, слои, структура каталогов, паттерны и запреты, именование, ошибки, логирование, БД, API, тесты, журнал архитектурных решений; короткий файл правил для ИИ-агента со ссылками на стандарт (архитектор) | — (входит в контекст всех этапов, где ИИ пишет код) | Каркас проекта: структуру каталогов, конфигурацию, общие базовые классы |
| 4 | Данные | DR для сущностей, которые функциональность хранит; системные NFR | Технический стандарт, DR, NFR | Миграции БД, модели данных, права доступа БД |
| 5 | Глобальные функциональности | Глобальные SF: их FR, AR, UI, AC | Технический стандарт, глобальные SF | Общие механизмы: обработка ошибок, блокировки, пагинация, сортировка, уведомления |
| 6 | Бэкенд по каждой SF | FR, затем AR (бизнес-логика, валидации, операции API) | Технический стандарт, UC, DR, FR и AR этой SF, подключённые глобальные SF | Контроллеры, сервисный слой, схема API |
| 7 | Фронтенд по каждой SF | UI: экран одной SF описывается в её FR, экран общий для нескольких SF записывается на уровне F | Технический стандарт, UC, FR, AR и UI, UI-kit | Экраны, формы, навигация, подключение к API на компонентах UI-kit |
| 8 | Проверка по каждой SF | AC к каждому FR и к экранам | Технический стандарт, AC | Автотесты API и сквозные тесты интерфейса |

Экран ссылается на UI-kit и описывает только отклонения от него. Этап 2 не зависит от этапов 4–6 и может идти
параллельно с ними, но должен завершиться до этапа 7. Этап 3 должен завершиться до первого этапа, на котором ИИ
пишет код (этап 4): иначе каждая SF получит собственный стиль и структуру кода. Глобальные SF подключаются к FR
атрибутом `Использует`, заново их поведение не описывается.

Требования определяют поведение системы, технический стандарт определяет технику его реализации. Стек и среду,
которые приняты как данность, записывают в `CON` и `SR`, а технический стандарт ссылается на них и не копирует.
Если требование противоречит техническому стандарту, ИИ не выбирает сторону сам, а заводит вопрос `Q` для владельца
решения.

Количество требований определяется каталогом SF: чем больше SF, тем больше пунктов. Минимальный состав пакета:

| Уровень | Обязательно | По необходимости |
|---|---|---|
| **F** | цель и границы, хотя бы один UC, каталог SF | DR (если функциональность хранит данные), EI, NFR, общий UI |
| **SF** | хотя бы один FR, AR для каждой операции API, хотя бы один AC на каждый FR | DR уровня SF, отдельные UI, NFR и BR (см. «Допустимые упрощения») |

ID, статусы и связи между требованиями вводятся поэтапно: сначала ID (на них ссылаются остальные пункты), затем 
связи, затем статусы. До ввода ID пункты называют заголовком и ссылаются на них по заголовку.
