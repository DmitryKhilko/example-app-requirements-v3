# ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ {#fr}

Здесь собраны требования, общие для нескольких детальных функциональностей справочника: тестовый набор, проверки
полей записи и события журнала аудита, а также перечень ручных проверок.

## Тестовый набор данных {#fr-pt-fixture .collapsed}

Критерии приёмки всех детальных функциональностей справочника опираются на набор из 15 записей, снятых со
скриншотов. Набор лежит в файле `api/PT.fixture.json`; время в нём — UTC, на экране оно показывается в UTC+3
([NFR-004][]). Перед каждым сценарием справочник очищается и заполняется этим набором, если в сценарии не сказано
иное. Идентификаторы записей, кроме первых двух, имеют вид `00000000-0000-4000-8000-0000000000NN`, где `NN` — номер
записи в наборе.

```json
--8<-- "requirements/features/dict-product-type/api/PT.fixture.json"
```

## FR-PT-001. Проверка полей записи вида изделий {#fr-pt-001 .collapsed}

- **Использует**: [F-PT][], [DR-PT-001][], [AR-001][]
- **Используется в**: [FR-PT-CREATE-002][], [FR-PT-UPDATE-002][], [UI-PT-001][]
- **Описание**: Единый перечень проверок полей записи при создании и изменении: какой код ошибки возвращает API и
какой текст показывает форма. Ограничения полей заданы в [DR-PT-001][]; общие правила (лишние поля, `null`) — в
[AR-001][].
- **Условие**: Пользователь отправляет данные записи на создание ([AR-PT-CREATE-001][]) или изменение
([AR-PT-UPDATE-001][]), в том числе через форму [UI-PT-001][].
- **Результат**: Каждое значение, которое не проходит проверку, даёт элемент `details` с кодом из таблицы (API) и
текст ошибки под полем (форма). Значение `null` приравнивается к отсутствию поля.

| Поле | Проверка | Код в `details` | Текст под полем формы |
| :--- | :--- | :--- | :--- |
| `name_nominative` | Поле передано | `REQUIRED` | Введите наименование |
| `name_nominative` | Значение — строка | `INVALID_TYPE` | — (форма передаёт строку) |
| `name_nominative` | После обрезки пробелов по краям не пустое | `BLANK` | Введите наименование |
| `name_nominative` | После обрезки не длиннее 150 символов | `TOO_LONG` | — (форма не даёт ввести больше) |
| `product_group` | Поле передано | `REQUIRED` | Выберите тип изделия |
| `product_group` | Одно из значений [DR-PT-001][] | `INVALID_VALUE` | — (форма предлагает только их) |
| Натиры (оба поля) | Поле передано | `REQUIRED` | Введите количество |
| Натиры (оба поля) | Значение — число | `INVALID_TYPE` | — (форма не даёт ввести не число) |
| Натиры (оба поля) | Больше 0 | `OUT_OF_RANGE` | Значение должно быть больше 0 |
| Натиры (оба поля) | Не больше 999.99 | `OUT_OF_RANGE` | Значение должно быть не больше 999,99 |
| Натиры (оба поля) | Не более 2 знаков после точки | `INVALID_SCALE` | Не более 2 знаков после запятой |
| `stamp_impressions_count` | Поле передано | `REQUIRED` | Введите количество |
| `stamp_impressions_count` | Значение — целое число | `INVALID_TYPE` | Введите целое число |
| `stamp_impressions_count` | Больше 0 | `OUT_OF_RANGE` | Значение должно быть больше 0 |
| `is_active` | Значение — `true` или `false` | `INVALID_TYPE` | — (переключатель) |

Натиры — поля `default_streak_count` и `wholesale_gold_streak_count`. Обязательность `is_active` зависит от операции:
при создании поле необязательно ([DR-PT-CREATE-001][]), при изменении обязательно ([DR-PT-UPDATE-001][]).
Уникальность наименования в типе проверяется после этих проверок и даёт ответ `409`.

Проверяется критериями приёмки [FR-PT-CREATE-002][], [FR-PT-UPDATE-002][] и [UI-PT-001][].

## FR-PT-002. Журнал аудита справочника {#fr-pt-002 .collapsed}

- **Использует**: [F-PT][], [NFR-003][]
- **Используется в**: [FR-PT-CREATE-001][], [FR-PT-UPDATE-001][], [FR-PT-ACTIVATION-001][], [FR-PT-DELETE-001][]
- **Описание**: Какие события справочника видов изделий система записывает в журнал аудита и с какими данными. Общие
правила журнала (состав записи, транзакционность, неизменность) заданы в [NFR-003][].
- **Условие**: Операция изменения данных справочника завершилась успешно.
- **Результат**: В журнале аудита появляется запись с операцией из таблицы.

| Операция | Когда | Данные записи справочника в журнале | Требование |
| :--- | :--- | :--- | :--- |
| `CREATE` | Запись создана | Все поля созданной записи | [FR-PT-CREATE-001][] |
| `UPDATE` | Изменены поля (не только статус) | Прежние и новые значения изменённых полей | [FR-PT-UPDATE-001][] |
| `STATUS_CHANGE` | Изменён только статус | Прежнее и новое значение `is_active` | [FR-PT-ACTIVATION-001][] |
| `DELETE` | Запись удалена | Все поля записи на момент удаления | [FR-PT-DELETE-001][] |

- Один запрос изменения даёт одну запись журнала: если вместе со статусом изменены другие поля, это `UPDATE`, а
  `is_active` входит в изменённые поля.
- Удаление нескольких записей даёт по одной записи журнала на каждую удалённую запись.
- Запрос изменения без новых значений, чтение списка и чтение записи в журнал не пишутся.

### Критерии приёмки (AC) {#fr-pt-002-ac .collapsed}

```gherkin
# language: ru
@FR-PT-002 @NFR-003
Функционал: Журнал аудита справочника

  Предыстория:
    Дано в справочнике записи из файла "PT.fixture.json"
    И аутентифицированный пользователь с ролью "ais"

  Сценарий: Создание
    Когда он создаёт запись с телом из файла "AR-PT-CREATE-001.request.json"
    Тогда в журнале аудита одна новая запись с операцией "CREATE" и всеми полями созданной записи
    И в записи журнала указаны пользователь, его роли, дата и время в UTC

  Сценарий: Изменение наименования и статуса одним запросом
    Когда он изменяет запись "Броши": наименование на "Брошки", "is_active" на false
    Тогда в журнале аудита одна новая запись с операцией "UPDATE"
    И изменёнными полями "name_nominative" и "is_active" с прежними и новыми значениями

  Сценарий: Изменение только статуса
    Когда он изменяет у записи "Броши" только "is_active" на false
    Тогда в журнале аудита одна новая запись с операцией "STATUS_CHANGE", прежним значением true и новым false

  Сценарий: Удаление двух записей
    Когда он удаляет записи с телом из файла "AR-PT-DELETE-001.request.json"
    Тогда в журнале аудита две новые записи с операцией "DELETE" и данными записей "Брелоки" и "Броши"

  Сценарий: Чтение не пишется в журнал
    Когда он запрашивает список и запись "Броши"
    Тогда в журнале аудита не появилось новых записей
```

## Ручные проверки {#fr-pt-manual .collapsed}

Сценарии с тегом `@manual` не автоматизируются: для них нужна недоступная в автотестах среда (сбой хранилища,
таблица-потребитель, оценка человеком). Их выполняют перед сдачей функциональности по этому перечню.

| Требование | Сценарий | Что нужно для проверки |
| :--- | :--- | :--- |
| [AR-001][] | Внутренняя ошибка не раскрывает технических подробностей | Отключить хранилище данных на стенде |
| [NFR-002][] | Работа без мыши | Тестировщик с клавиатурой и экранным диктором |
| [FR-PT-UPDATE-001][] | Сбой журнала аудита отменяет изменение | Запретить запись в журнал на стенде |
| [FR-PT-DELETE-001][] | Сбой журнала аудита отменяет удаление | Запретить запись в журнал на стенде |
| [FR-PT-DELETE-002][] | Одна из записей используется — не удаляется ни одна | Тестовая таблица-потребитель |
| [FR-PT-DELETE-003][] | Запись используется | Тестовая таблица-потребитель |
| [FR-PT-ACTIVATION-001][] | Деактивация используемой записи | Тестовая таблица-потребитель |

Перечень обновляется вместе с критериями приёмки: появился или исчез сценарий `@manual` — меняется таблица.
