# ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ {#fr}

Критерии приёмки проверяются на каждой операции изменения, которая подключает функциональность. Эталонная
реализация — изменение вида изделий (`PUT /api/v1/product-types/{pk}`, форма с приставкой `data-testid` `pt`) с
[тестовым набором][fixture]. Скриншотов одновременного изменения нет: экран описан по общим правилам формы и
уведомлений.

## FR-G-LOCK-001. Проверка версии записи {#fr-g-lock-001 .collapsed}

- **Использует**: [SF-G-LOCK][], [AR-001][], [NFR-004][]
- **Используется в**: [UI-G-LOCK-001][], [FR-PT-UPDATE-002][]
- **Описание**: Операция изменения сравнивает версию записи из запроса с текущей и отклоняет изменение устаревшей
версии.
- **Условие**: Пользователь вызывает операцию изменения, которая подключает [SF-G-LOCK][]; проверки аутентификации,
прав, данных и существования записи пройдены.
- **Результат**:
    - Версия записи — поле `updated_at` в теле запроса: значение, полученное клиентом при чтении записи. Поле
      обязательно; без него — `400` с кодом `REQUIRED`.
    - Значения сравниваются с точностью до секунды в UTC ([NFR-004][]).
    - Совпадает — проверка пройдена, операция продолжает свои проверки.
    - Не совпадает — ответ `409` с кодом `RECORD_MODIFIED` и эталоном
      [error.409.modified.json](../api/error.409.modified.json); запись не меняется, в журнал аудита ничего не
      пишется.
    - Проверка версии идёт после проверки существования записи (`404`) и раньше остальных правил предметной области
      (например, уникальности) ([AR-001][]).
    - Успешное изменение записывает в `updated_at` новое время; ответ содержит его, чтобы клиент мог изменять запись
      дальше без повторного чтения.

### Критерии приёмки (AC) {#fr-g-lock-001-ac .collapsed}

```gherkin
# language: ru
@FR-G-LOCK-001 @SF-G-LOCK
Функционал: Проверка версии записи

  Предыстория:
    Дано в справочнике видов изделий записи из файла "PT.fixture.json"
    И аутентифицированный пользователь с ролью "ais"

  Структура сценария: Устаревшая версия
    Когда он отправляет "<операция>" для записи "<запись>" с "updated_at" = "<версия>"
    Тогда код ответа равен 409
    И тело ответа равно содержимому файла "error.409.modified.json"
    И запись не изменилась и в журнале аудита нет новых записей

    Примеры:
      | операция                       | запись               | версия               |
      | PUT /api/v1/product-types/{pk} | Зажимы для галстуков | 2026-11-23T08:36:43Z |

  Структура сценария: Версия без поля
    Когда он отправляет "<операция>" для записи "<запись>" без поля "updated_at"
    Тогда код ответа равен 400
    И "details" содержит ошибку с полем "updated_at" и кодом "REQUIRED"

    Примеры:
      | операция                       | запись               |
      | PUT /api/v1/product-types/{pk} | Зажимы для галстуков |

  Структура сценария: Версия проверяется раньше уникальности
    Когда он отправляет "<операция>" для записи "<запись>" с устаревшим "updated_at" и наименованием "Броши"
    Тогда код ответа равен 409 с кодом "RECORD_MODIFIED"

    Примеры:
      | операция                       | запись               |
      | PUT /api/v1/product-types/{pk} | Зажимы для галстуков |

  Сценарий: Два пользователя изменяют одну запись
    Дано пользователи А и Б прочитали запись "Зажимы для галстуков"
    Когда пользователь А сохраняет новое наименование "Зажимы"
    И пользователь Б сохраняет новое наименование "Зажимы галстучные" с прочитанной версией
    Тогда пользователь А получает код 200, пользователь Б — код 409 с кодом "RECORD_MODIFIED"
    И наименование записи — "Зажимы"
```
